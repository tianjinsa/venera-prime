# 多设备 WebDAV 备份停留在旧数据的排查

## 输入文件与结论

检查 `1792228143585082.venera`，只读取备份内容，未导入运行其中的源脚本，也未访问用户的 WebDAV 服务。

- ZIP 完整性检查通过，包含的五个 SQLite 数据库均通过完整性检查。
- `dataVersion` 为 `3687`，没有自定义排除同步字段。
- `history.db` 与 `local_favorite.db` 的 SQLite 文件头读写格式均为 `2`，即 WAL 模式。
- 备份未包含设备独立的 `webdavAutoSync` 开关，无法据此判断各设备是否已开启自动同步。

导出代码此前仅为 Cookie 数据库生成 SQLite 快照，历史、收藏、稍后阅读与统计数据库均直接读取主文件。WAL 模式下，已提交的新记录可能仍在 `-wal` 文件中，复制主文件会漏掉这些记录。这是能够复现“应用数据更新而备份内容仍旧”的明确缺陷；原文件本身无法证明用户远端还遇到了哪些传输问题。

## 修复

- 所有导出的 SQLite 数据库统一使用 `VACUUM main INTO` 生成独立快照，包含已提交的 WAL 记录；自动同步与手动备份共用此逻辑。
- 备份日期及版本按数字排序，避免 `9` 与 `10` 等位数变化时选错新旧。
- 上传版本递增至本地及远端已知版本之后；文件名增加时间戳与随机标识，避免多个设备生成同名文件。
- 上传失败恢复本地版本号；清理时保留相同版本的并发备份及更新的备份。
- 下载按设备独立、按目标隔离的备份标识判断是否已同步，不再以本地计数器较大或相等直接跳过不同内容。
- 新格式使用唯一文件名标识；旧格式结合 ETag、修改时间和大小。旧格式缺少可靠元数据时重新读取文件。
- 恢复数据库及源管理器产生的通知不再触发回传，避免设备之间反复上传已恢复的数据。

自动同步开关仍由各设备独立控制。同步仍采用整包快照，不会自动合并多个设备同时产生的不同修改。所有参与设备需要使用修复后的版本，才能完整采用新的备份选择及上传逻辑。

已有备份不会因为代码修复而补回先前未打包的 WAL 内容；使用修复版时，应从保有最新、最完整数据的设备重新上传。
